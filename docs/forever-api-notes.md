# WoW: Forever - API Notes

Findings verified against the `forever` branch of [wow-ui-source](https://github.com/Gethe/wow-ui-source/tree/forever) and the live client (1.60.1).

## Client identity

- WoW: Forever is the internal project **Camelot**: `WOW_PROJECT_ID == WOW_PROJECT_CAMELOT` (`18`)
- `.toc` interface version: `## Interface: 16001`
- It runs the **modern Mainline FrameXML** (retail 12.x API) with `Camelot` overrides, for example `Blizzard_Minimap/Camelot/`
  - In Blizzard `.toc` files, `[Game]` paths resolve to `Camelot` and `[Family]` paths to `Mainline`
  - Game content is vanilla (spells, talents, creature types), the API is modern (`C_Spell`, `C_AddOns`, `C_Minimap`, `Settings`, ...)
- Third-party AddOns use the `_Camelot.toc` (and sometimes `_Forever.toc`) multi-TOC suffix

## Secret values (AddOn restrictions)

- Some API results are **secret values** for AddOn (tainted) code: they can be stored and passed to some widget APIs,
  but comparing them, doing math with them or concatenating them raises a Lua error
  - Using a secret as a table key is allowed, but it makes every lookup in that table return secrets (`SecretWhenLuaTableHasSecretKeys`)
- Always test with `issecretvalue(value)` **before** any comparison, including `== nil`
- `C_Secrets.HasSecretRestrictions()` tells whether the client build uses secrets at all (it does on Forever)
- Restriction states (`Enum.AddOnRestrictionType`): `Combat`, `Encounter`, `ChallengeMode`, `PvPMatch`, `Map`, `Chat`
  - `C_RestrictedActions.IsAddOnRestrictionActive(type)`, event `ADDON_RESTRICTION_STATE_CHANGED`
- Known secret sources:
  - `UnitCastingInfo` / `UnitChannelInfo` for any unit other than the player and their pet
  - Unit identity (`UnitName`, `UnitCreatureType`, ...) of units that are not player-controlled and not in the group
    - Verified in game: `UnitCreatureType("target")` of a mob is **not** secret out of combat, so this applies while a restriction state is active (in-combat secrecy assumed, not yet observed)
    - Check `C_Secrets.ShouldUnitIdentityBeSecret(unit)` or `issecretvalue` at runtime
  - `UnitHealth` (`SecretReturns`), unit stats (`UnitAttackSpeed`, `UnitRangedDamage`) while restricted
  - `C_Spell.GetSpellCooldown` while restricted; its `isActive` and `isOnGCD` fields are never secret
  - Target/focus auras (`C_UnitAuras.*`) while restricted
  - Tooltip data of restricted units (seen in `Logs/General.log`: "attempt to index local 'color' (a secret table value, while execution tainted by ...)")

## No combat log

- `C_CombatLog.GetCurrentEventInfo` is not exposed to AddOns, so `COMBAT_LOG_EVENT_UNFILTERED` is useless
- Use dedicated events instead, for example the swing timer below

## Swing timer

- `PLAYER_SWING(swingDuration, swingType)` with `Enum.PlayerSwingType`: `MainHand = 0`, `OffHand = 1`, `Ranged = 2`
- `PLAYER_SWING_RANGE_UPDATE(swingType, isInRange, checksRange)`
- `C_SwingTimer.EnableRangeCheck(swingType, enable)`, `C_SwingTimer.IsTargetWithinSwingRange(swingType)`
- Blizzard's own implementation: `Blizzard_SwingTimer`

## Minimap tracking

- `C_Minimap.GetNumTrackingTypes()`, `C_Minimap.GetTrackingInfo(index)` returns `{ name, texture, active, type, subType, spellID }`
  - `subType == 1` is Hunter tracking (`HUNTER_TRACKING`)
- `C_Minimap.SetTracking(index, on)` switches tracking (`CastSpellByName` is not available to AddOns)
- Event: `MINIMAP_UPDATE_TRACKING`

## Range checks

- `C_Spell.IsSpellInRange(spell, unit)` returns `true` / `false` / `nil` (`nil` when the range check is invalid, per the API docs); not flagged as secret; accepts spell IDs or names (that a name matches the rank you know is not yet verified in game)
- `C_Spell.GetSpellInfo(spell)` returns a table with `minRange` / `maxRange`
- `CheckInteractDistance`, `C_Item.IsItemInRange` exist; [LibRangeCheck-3.0](https://github.com/WeakAuras/LibRangeCheck-3.0) supports Forever since v38 (`isForever`), v39 also handles secret GUIDs
  - Its distance steps for hostile units on Forever/Era come from item range checks: 5, 10, 15, 20, 25, 30, 35, 40, 45, 100 yards (plus class spells such as Auto Shot); the interact distance checks (8 and 28 yards) are only used while no item data is cached, for example right after login
  - When every check fails it returns the largest cached step and `nil`, e.g. `(100, nil)` or `(45, nil)` while the 100 yard item is not cached; in combat it only skips item checks on units you cannot attack (not yet verified in game)
  - With secret GUIDs it caches by unit token, so pass `maxCacheAge = 0` to `GetRange` right after a target change
- `UnitCanAttack`, `UnitIsDeadOrGhost` are not flagged as secret
- `Region:SetAlphaFromBoolean(value, alphaIfTrue, alphaIfFalse)` accepts secret booleans (shows/hides a region based on a secret result)

## Nameplates

- `C_NamePlate.GetNamePlateForUnit(unit)` (the `"target"` unit token is used for the target's plate), events `NAME_PLATE_UNIT_ADDED` / `NAME_PLATE_UNIT_REMOVED` (the plate is still returned while `REMOVED` is dispatched)
- Blizzard's health bar: `plate.UnitFrame.HealthBarsContainer.healthBar`; the Camelot level frame sits to the right of it
- Plater keeps its own unit frame on `plate.unitFrame` with `plate.unitFrame.healthBar`; its level text is anchored above the top right corner of the health bar by default

## Spell casts

- `UNIT_SPELLCAST_SUCCEEDED` (`unitTarget, castGUID, spellID, castBarID`) is flagged `SecretWhenUnitSpellCastRestricted`; `C_Secrets.ShouldUnitSpellCastingBeSecret(unit)` / `ShouldUnitSpellCastBeSecret(unit, spell)` tell when; guard `spellID` with `issecretvalue` (ForeverHawkTimer counts such casts in `/fht debug`, not yet verified whether the player's own casts are ever secret)
- Register it with `frame:RegisterUnitEvent("UNIT_SPELLCAST_SUCCEEDED", "player")` for the player's own casts
- `C_Spell.GetSpellName(spellID)` / `C_Spell.GetSpellTexture(spellID)` take secret arguments (`AllowedWhenTainted`) and return nothing for unknown spells
- Forever-only spells use new high IDs (game data, not in wow-ui-source; from the in-game tooltip and warcraft.wiki.gg): **Summon Hawk** (Beast Mastery talent, 4 ranks, added in 1.60.1) is 1293241 (rank 1) and 1293527 (rank 4), ranks 2 and 3 are unknown, so match the spell name; the hawk stays 18 sec and only 2 hawks can be active at once (tooltip)

## Damage meter

- `C_DamageMeter` is Blizzard's built-in meter data (no combat log): `GetAvailableCombatSessions`, `GetCombatSessionFromType/FromID` and `GetCombatSessionSourceFromType/FromID` (the last four are `SecretWhenInCombat`), `IsDamageMeterAvailable()` returns `isAvailable, failureReason`; session types `Overall` 0, `Current` 1, `Expired` 2
- Blizzard's meter window is shown only with the CVar `damageMeterEnabled` on, the meter available and its visibility setting allowing it (`Blizzard_DamageMeter/DamageMeter.lua` `ShouldBeShown`); the checkboxes for `damageMeterEnabled` and `damageMeterResetOnNewInstance` (reset on new instance) are registered in `Blizzard_SettingsDefinitions_Frame/AdvancedOptions.lua`
- In combat the source fields `totalAmount` / `amountPerSecond` and the session `totalAmount` are secret, so AddOns cannot divide them; Blizzard's own meter computes the percentage in secure code (`Blizzard_DamageMeter/DamageMeterEntry.lua`, numbers setting `Complete`)
- Secret-safe display helpers: `AbbreviateNumbers` / `AbbreviateLargeNumbers` / `BreakUpLargeNumbers` take secret numbers (`AllowedWhenTainted`); custom `breakpointData` entries need `abbreviationIsGlobal = false` for raw suffixes, and `CreateAbbreviateConfig(breakpoints)` (call it in `pcall`, it errors on rejected breakpoints) gives a cached `config`; `C_CurveUtil` curves only take secrets from untainted code
- Percentage of two secret numbers without math (Skada port, not yet verified in game): `StatusBar:SetMinMaxValues` / `SetValue` accept secrets (`AllowedWhenTainted`, they add the `BarValue` secret aspect to the bar), and a bar exactly 100 units wide should have a fill texture width equal to the percentage; `GetWidth` is `SecretWhenAnchoringSecret`, so the width is expected to come back secret and only goes to `string.format` for display; Skada uses it only after a self-test with plain numbers shows that the fill width follows `SetValue` immediately
- `FontString:SetFormattedText` takes secret arguments (`AllowedWhenTainted`, adds the `Text` aspect), so it can compose secret names or numbers with other text; Lua's `string.format` is known to work with secret numbers (`%.0f`), for secret strings prefer `SetFormattedText`
- Reported, not verifiable in wow-ui-source: calling `C_DamageMeter.ResetAllCombatSessions()` again in response to a reset (from `DAMAGE_METER_RESET`) can leave the native meter unable to attribute damage until `/reload`, so Blizzard's meter and every addon meter stay empty ([skada#9](https://github.com/zarnivoop/skada/issues/9), fixed in Skada 2.6.2, our backport also skips resets within 2 s of another one)

## Edit Mode

- `EventRegistry:RegisterCallback("EditMode.Enter" / "EditMode.Exit", func, owner)` (used by Blizzard's Camelot `MainMenuBarEndCaps.lua`); the CallbackRegistry runs every callback through `securecallfunction`, so addon callbacks do not taint Edit Mode
- `EditModeManagerFrame:IsEditModeActive()` tells whether Edit Mode is open; it stays true while Blizzard hides Edit Mode for a moment without leaving it (`CheckHideAndLockEditMode`: Quick Keybind mode, Action Bar / Raid Frame settings, Cooldown Viewer), which fires no `EditMode.Exit`, so also follow `EditModeManagerFrame:IsShown()` (`HookScript` its `OnShow` / `OnHide`)
- AddOn frames cannot join Blizzard's Edit Mode systems; ForeverHawkTimer shows its own drag overlay while Edit Mode is open, with Blizzard's look: a `NineSliceCodeTemplate` frame and `NineSliceUtil.ApplyLayout(frame, layout, "editmode-actionbar-highlight")` (`"editmode-actionbar-selected"` for the yellow look) with a copy of the local `EditModeSystemSelectionLayout` from `Blizzard_EditMode/Shared/EditModeSystemTemplates.lua`
- Snapping like Edit Mode: `EditModeManagerFrame:IsSnapEnabled()` is the `Snap to Elements` checkbox; Blizzard's magnetism range is `EditModeMagnetismManager.magnetismRange` (8), compared with `distance * UIParent:GetEffectiveScale()` (`EditModeUtil.lua`, `CheckReplaceMagneticFrameInfo`), and its preview lines are red `Line`s anchored to `UIParent` with `PixelUtil.GetNearestPixelSize(1.5, line:GetEffectiveScale(), 1.5)` thickness in a HIGH strata container above the Edit Mode highlights (`EditModeTemplates.lua`/`.xml` `MagnetismPreviewLineTemplate`, `EditModeManager.xml` `MagnetismPreviewLinesContainer`); ForeverHawkTimer copies this for its center snap
- Movable addon frames: `SetMovable(true)`, `SetClampedToScreen(true)`, `SetDontSavePosition(true)` (keeps the position out of the client's own layout file, the AddOn saves it), `StartMoving()` / `StopMovingOrSizing()`

## Settings panel (Esc -> Options -> AddOns)

- Canvas pages: `Settings.RegisterCanvasLayoutCategory(frame, name)`, `Settings.RegisterCanvasLayoutSubcategory(parentCategory, frame, name)`, then `Settings.RegisterAddOnCategory(category)` for the top level category
- Optional frame callbacks: `frame.OnRefresh`, `frame.OnDefault` (only reached through "Restore All Defaults"), `frame.OnCommit`
- Canvas pages hide the settings list, including its `Defaults` button, so a canvas panel needs its own button
- `Settings.OpenToCategory(category:GetID())` calls `C_SettingsUtil.OpenSettingsPanel`, which `HasRestrictions`: only call it from a user click and never in combat
  - The minimap button of the shared file (FRV-120) calls it from its own `OnClick` and, through an overview button's `Click()`, from a `MenuUtil.CreateContextMenu` entry's callback, which runs inside the click on the menu entry (not yet verified in game)
- Templates that exist: `UICheckButtonTemplate` (`.Text`, aliased as `.text`), `UIRadioButtonTemplate` (`.text`), `UISliderTemplateWithLabels` (`.Text`, `.Low`, `.High`), `UIPanelButtonTemplate`
- `InterfaceOptionsCheckButtonTemplate` / `OptionsSliderTemplate` only exist in `DeprecatedTemplates.xml`, avoid them
- Color picker: `ColorPickerFrame:SetupColorPickerAndShow({ r, g, b, hasOpacity, swatchFunc, cancelFunc })`, read the color with `ColorPickerFrame:GetColorRGB()`
  - With opacity (`Blizzard_ColorPickerFrame/Mainline/ColorPickerFrame.lua`, the `[Family]` file Camelot loads; verified against the source for ForeverCampFeatures 1.1.0, FRV-122, not yet verified in game): `opacity` in the info is the alpha (1 = opaque) the alpha slider starts at, `opacityFunc` runs with `swatchFunc` on every change and on Okay, `ColorPickerFrame:GetColorAlpha()` reads it, and `cancelFunc(previousValues)` gets `{ r, g, b, a }` back on Cancel, Escape or a click outside the picker
- A canvas page taller than the settings area (about 600 high, `Blizzard_SettingsPanel.xml`: 724 high less the header and footer) is cut off; `CreateFrame("ScrollFrame", name, panel, "ScrollFrameTemplate")` (`SecureUIPanelTemplates.xml`) adds a `MinimalScrollBar` at its right edge and the mouse wheel (`ScrollUtil.InitScrollFrameWithScrollBar`), with the page as `SetScrollChild(frame)` (ForeverCampFeatures 1.1.0, not yet verified in game)
- Dropdowns: `CreateFrame("DropdownButton", name, parent, "WowStyle1DropdownTemplate")` with `SetupMenu(function(dropdown, root) ... end)`; the menu is built again every time it opens (`DropdownButtonMixin:OpenMenu`), `root:SetScrollMode(height)` makes a long menu scroll, and an entry's `SetOnEnter(function(button, description) ... end)` / `SetOnLeave` run on hover with `description:GetData()` the radio's value (`Blizzard_Menu/Menu.lua`); `dropdown:OverrideText(text)` shows a fixed text the dropdown no longer works out itself, `SetEnabled(false)` greys it. The menu has no search element and no Blizzard menu builds one (ForeverCampFeatures 1.1.0, not yet verified in game)
- Input boxes on canvas pages: Settings calls `OnRefresh` on every canvas page while it still has no parent or anchors (0 width), and `EditBox:SetText()` then leaves the box scrolled so the text is invisible until the user types (seen in game with ForeverHawkTimer 1.1.0); call `editBox:SetCursorPosition(0)` after every `SetText` (Blizzard's documented workaround in `Blizzard_AuctionHouseSellFrame.lua`, not yet confirmed in game for our panel; fallback: set the text again one frame later)

## Chat

- `ChatFrameEditBoxTemplate` has `ignoreArrows="true"`, plain Up/Down never reach the edit box (only Alt + Up/Down)
- Sent lines go through `editBox:AddHistoryLine(text)`, the focused box is `ChatFrameUtil.GetActiveWindow()`
- Shift+click of an item (a bag slot, a chat link, a row of the Auction House) goes through `HandleModifiedItemClick` to `ChatFrameUtil.InsertLink(link)` (`Blizzard_ChatFrameBase/Mainline/ChatFrameUtilOverrides.lua`; `ChatEdit_InsertLink` is its deprecated alias in `Blizzard_DeprecatedChatInfo`). It fills the macro text, the profession search, the communities chat or the active chat box (and gives that box the focus), else, while `AuctionHouseFrame` is visible, the AH's search box (`SetSearchText`). Verified against the source only: ForeverMarket 1.34 (FRV-41) puts the item into its sniper's item box with `hooksecurefunc(ChatFrameUtil, "InsertLink", ...)` while that box has the focus (not yet verified in game)
- Clickable links of an AddOn's own (verified against wow-ui-source `forever` for FRV-180, not yet verified in game; the shared file's `[versions]` link): a chat line may hold `|Haddon:<data>|h[text]|h` (`LinkTypes.AddOn = "addon"`, `Blizzard_SharedXML/LinkUtil.lua`). A click goes `ChatFrameMixin:OnHyperlinkClick` -> `SetItemRef` (`Blizzard_UIPanels_Game/Mainline/ItemRef.lua`, the `[Family]` file) -> `LinkUtil.ProcessLink`, whose `addon` handler (`Shared/ItemRefHandlersShared.lua`, "local links only") runs `EventRegistry:TriggerEvent("SetItemRef", link, text, button, frame)`; `link` is the part between `|H` and `|h` (`addon:<data>`). An AddOn listens with `EventRegistry:RegisterCallback("SetItemRef", function(owner, link, text, button, frame) ... end, owner)`: one callback per owner (registering again with the same owner replaces it), every owner's callback sees every `addon:` link, so each checks its own data. Hovering fires `EventRegistry`'s `ChatFrame.OnHyperlinkEnter` (`Blizzard_ChatFrameBase/Shared/ChatFrame.lua`)

- AddOn messages and channels (verified against wow-ui-source `forever` for FRV-116, not yet verified in game; ForeverCampFeatures 1.0 shares through them, `/fcf debug` prints what the live client answers):
  - `C_ChatInfo.SendAddonMessage(prefix, message, chatType, target)` (`SecretArguments = "NotAllowed"`) returns `Enum.SendAddonMessageResult`: `Success` 0, `InvalidPrefix` 1, `InvalidMessage` 2, `AddonMessageThrottle` 3, `InvalidChatType` 4, `NotInGroup` 5, `TargetRequired` 6, `InvalidChannel` 7, `ChannelThrottle` 8, `GeneralError` 9, `NotInGuild` 10, `AddOnMessageLockdown` 11, `TargetOffline` 12 (`ChatConstantsDocumentation.lua`); `C_ChatInfo.RegisterAddonMessagePrefix(prefix)` returns `RegisterAddonMessagePrefixResult`; `CHAT_MSG_ADDON(prefix, text, channel, sender, target, zoneChannelID, localID, name, instanceID)` carries no secret flag
  - `C_ChatInfo.AreOutgoingAddonChatMessagesRestricted()` is "controlled on a realm-by-realm basis (tournament realms allow it), and the ability for addons to receive comms is controlled separately"; `C_ChatInfo.InChatMessagingLockdown()` is true while "API security restrictions regarding chat messaging are in effect", and `Enum.AddOnRestrictionType.Chat` (5) is the matching restriction state
    - The realm flag's only Blizzard caller loads the tournament realm feature `CooldownBroadcaster` when it is false (`Blizzard_Game/Mainline/EventImplementation.lua`), and `C_Commentator.SendAddonMessage` "works the same as C_ChatInfo.SendAddonMessage but accepts secrets and is only allowed when outgoing addon comms are allowed (i.e. on tournament realms)" (`CommentatorFrameDocumentation.lua`). So the flag is expected to be true on normal realms and to concern the secret-accepting route, not `C_ChatInfo.SendAddonMessage` with plain arguments; ForeverCampFeatures only prints it in `/fcf debug` and reads each send's `SendAddonMessageResult` instead (what Forever's realms answer is not yet verified in game)
  - Custom channels exist: `/join` (`Blizzard_ChatFrameBase/Shared/SlashCommands.lua`) and Mainline's channel list (`Blizzard_Channels/Mainline/ChannelList.lua`, with the name alone) call `JoinPermanentChannel(name, password, chatFrameID, hasVoice)`; `LeaveChannelByName(name)` and `GetChannelName(name)` (0 while not joined) exist the same way. None is in the generated documentation, so the source cannot say whether AddOn code may call them (no `HasRestrictions` entry to read); `JoinTemporaryChannel` and `JoinChannelByName` appear nowhere in the branch. A channel joined this way is kept by the client and joined again at every login, like any `/join`ed channel (warcraft.wiki.gg on `JoinPermanentChannel`; not yet verified in game), so it outlives the AddOn that joined it until `LeaveChannelByName` or `/leave`
  - `/join` puts the channel into the default chat frame's Lua `channelList` itself, and a chat frame shows a channel's messages and notices only for channels in that list (`Blizzard_ChatFrameBase/Mainline/ChatFrameOverrides.lua`; `ChatFrame_CheckAddChannel` adds only regional channels on its own), so a channel joined with the name alone shows in no chat window. ForeverCampFeatures joins its channel so 10 seconds after entering the world (the game's own channels keep their numbers), and since 1.1.0 (FRV-119) joins or leaves it at once on the player's own change (`/fcf on` or `off`, a sharing option, Defaults; out of combat, else after the fight, with the 10 second check following); it tries a join or a leave that does not take at most 5 times, counted again from each such change, and stops after an `ADDON_ACTION_BLOCKED` / `ADDON_ACTION_FORBIDDEN` naming it (payload: the AddOn, the function)

## Minimap / world map

- The minimap has no `SetPlayerTexture` / `SetPlayerTextureHeight`, the engine player arrow cannot be resized
- Minimap buttons (FRV-120; the shared file `JimsForeverAddOns.lua` builds one this way, not yet verified in game): LibDBIcon-1.0 (Questie's copy, minor 56, which Questie runs on Forever) makes a `Button` child of `Minimap` (31 x 31, strata `MEDIUM` fixed, level 8 fixed, highlight 136477 `Interface\Minimap\UI-Minimap-ZoomButton-Highlight`, border 136430 `MiniMap-TrackingBorder`, background 136467 `UI-Minimap-Background`, an icon) and places it at an angle around `Minimap`'s center, `GetMinimapShape()` (defined by minimap AddOns, else round) deciding which quadrants are round. Forever's `WOW_PROJECT_ID` is not `WOW_PROJECT_MAINLINE`, so it takes the classic sizes: border 53 x 53 at the top left, background 20 x 20 at (7, -5), icon 17 x 17 at (7, -6)
- MinimapButtonButton (third-party, 1.24.18 with a `_Camelot.toc`, read from the maintainer's installed copy for FRV-120): about a frame after `PLAYER_LOGIN`, after one second and whenever its own button is clicked it collects LibDBIcon-1.0 and LibMapButton-1.1 buttons, the names on its whitelist, and every child of `Minimap` that has a name matching `^LibDBIcon10_`, `MinimapButton`, `MinimapFrame`, `MinimapIcon`, `[-_]Minimap[-_]` or `Minimap$` that does not end in a digit, is no pin (`^HandyNotes`, `^TomTom`, `^Questie`, `^GatherMate`, ...), is not a secure global and is neither protected nor forbidden. It reparents a collected button, clears its `OnDragStart` / `OnDragStop`, replaces its `SetPoint`, `ClearAllPoints`, `SetParent` and `SetScale` with no-ops, and `hooksecurefunc`s its `Show` and `Hide` to update its layout (so `SetShown` alone leaves its layout as it was)
- World map player arrow: `GroupMembersPinTemplate` pins, `pin.dataProvider:GetUnitPinSizesTable().player`, then `pin:SynchronizePinSizes()`
- The map hierarchy (verified against wow-ui-source `forever` for FRV-99, not yet verified in game; ForeverMarket 1.36's place filter, `trade/Places.lua`):
  - `C_Map.GetMapInfo(uiMapID)` returns `UiMapDetails` (`mapID`, `name`, `mapType`, `parentMapID`, `flags`) or nothing; `C_Map.GetMapChildrenInfo(uiMapID, mapType, allDescendants)` the maps under one; `C_Map.GetBestMapForUnit("player")` the map you are in ("only works for the player and party members"), nilable (`MapDocumentation.lua`). None is flagged secret or `HasRestrictions` (only `OpenWorldMap` is); their `SecretArguments = "AllowedWhenUntainted"`, so an AddOn passes plain numbers
  - `Enum.UIMapType`: `Cosmic` 0, `World` 1, `Continent` 2, `Zone` 3, `Dungeon` 4, `Micro` 5, `Orphan` 6 (`MapConstantsDocumentation.lua`); Blizzard's world map walks `parentMapID` up while it is above 0 (`Blizzard_WorldMap/Blizzard_WorldMapTemplates.lua`)
  - Events `ZONE_CHANGED`, `ZONE_CHANGED_INDOORS`, `ZONE_CHANGED_NEW_AREA` (no payload)
  - ForeverArtisan_Contacts saves a vendor's map as `mapID` (zone level: 1438 Teldrassil for a vendor in Dolanaar, whose `subzone` is "Dolanaar"; 1457 Darnassus) with `mapName` and `zone`; in the maintainer's saved data of 2026-11-22 one vendor of 137 has no `mapID` (zone "Deeprun Tram"). Whether the game puts Darnassus under Teldrassil (and Stormwind City under Elwynn Forest) or right under its continent is not known outside the game: ForeverMarket follows `parentMapID` either way

## Character names

Verified against wow-ui-source `forever` (1.60.1) for FRV-10, not yet verified in game by this repository.

- Characters have a first name and a surname: Camelot's own `Blizzard_FrameXMLUtil/Camelot/NameUtil.lua` reads `local name, surname = UnitName(unit)` (and the same from `UnitNameUnmodified`), so the second return is the surname here, where retail has the realm; the full name is `name .. Constants.CharacterNameSeparatorConsts.CHARACTERNAME_SURNAME_SEPARATOR .. surname` (a space)
- Character creation takes both and checks them together (`C_CharacterCreation.CreateCharacter(name, surname, ...)`, `CheckName(name, surname)` in `Blizzard_CharacterCreate/Camelot/Blizzard_CharacterCreate.lua`) while `C_CharacterCreation.AreRegionalUniqueNamesEnabled()`; in game `RegionalUniqueNamesEnabled()` tells whether surnames are on
- So a character is identified by both names together (or by `UnitGUID("player")`); a first name alone may repeat, also among one player's characters on a realm
  - Read the two parts with `UnitNameUnmodified("player")` and guard a missing surname: AceDB-3.0 builds its character key that way, `name .. " " .. surname` while `RegionalUniqueNamesEnabled()` (the copy in `backports/Skada/lib/AceDB-3.0/AceDB-3.0.lua`)
  - The source does not settle whether the first return of `UnitName("player")` is the first name alone (`NameUtil.GetUnitFirstName` in the same Camelot file splits it at the separator, "name can be both name + surname"). Seen in game (the maintainer's saved variables, 1.60.1, FRV-56): it is the first name alone, as ForeverArtisan says (`ForeverArtisan_Core/Alts.lua`): ForeverMarket's character key is "Elfiehu", while AceDB's key from `UnitNameUnmodified("player")` in Skada's and Quartz's saved variables is "Elfiehu Ntress" (first name, space, surname)
  - ForeverMarket keys its per-character data by that first return; since 1.23 (FRV-35) a second character with the same first name on one realm and faction gets its full name as its key, and each key remembers its character's `UnitGUID("player")` (`FM.PlayerName()`, `R.charInfo`); `FM.PlayerFullName()` builds the full name from `UnitNameUnmodified("player")` (FRV-70). `UnitGUID` is flagged `SecretWhenUnitIdentityRestricted` and guarded with `issecretvalue`
- `GetRealmName()` (documented in `ConnectionDocumentation.lua`, a `cstring`, no secret flag) returns an empty string on Forever since the client 1.60.1.71037 (2026-11-20). Seen in game (FRV-92): ForeverMarket's first session on that build saved its data under the key "-Alliance" (realm part empty) next to the old "CAMWOW EU4 Realm 2 PvP-Alliance", and ForeverArtisan, which keys characters "Name-Realm-GUIDPART", started a second entry "Elfiehu--00CB83C3" in every profession DB. The same build's Blizzard Lua stopped comparing realm names: `C_BattleNet.IsGameAccountOnSameRealm(gameAccountID)` and the new `hasRealmInfo` field of the game account info replace them (`Blizzard_FriendsFrame/Camelot/FriendsFrame.lua`, `UnitPopupSharedUtils.lua`)
  - `UnitGUID("player")` still names the server: "Player-<server>-<hex>" ("Player-6842-00CB83C3"); ForeverArtisan's GUIDPART is its last part. ForeverMarket 1.30.2 (`FM.RealmName`) finds the realm from the saved data by the character's GUID or its server when the name is empty
  - `UnitClass("player")` returns the class name and the class file (`"HUNTER"`): `local _, class = UnitClass and UnitClass("player")` keeps only the first return (a Lua `and` expression is one value), which is why every `R.chars` entry of ForeverMarket before 1.23 is `true`

## Bags and bank

Verified against wow-ui-source `forever` (1.60.1) for FRV-10. In game ForeverMarket already reads bags and the character bank through `C_Container` with `BANKFRAME_OPENED`, `BANKFRAME_CLOSED` and `PLAYERBANKSLOTS_CHANGED`; the `C_Bank` functions, `BANK_TABS_CHANGED` and everything about the account bank are verified against the source only (ForeverMarket 1.23 uses them for the account bank, below; not yet verified in game).

- Containers: `C_Container.GetContainerNumSlots(bag)` and `C_Container.GetContainerItemInfo(bag, slot)` (a table with `itemID`, `stackCount`, `isBound`, `hyperlink`, ...; nothing for an empty slot); neither is flagged secret

  - Events: `BANKFRAME_OPENED`, `BANKFRAME_CLOSED`, `PLAYERBANKSLOTS_CHANGED(slot)`, `BANK_TABS_CHANGED(bankType)`
  - ForeverMarket scans the character bank slot by slot (`CharacterBankTab_1`..`9` through `C_Container`) only while the bank is open and keeps the last reading per character (`R.bank`, `trade/Sources.lua`, `scan/Worth.lua`)
- Account bank: the Camelot frame also handles `Enum.BankType.Account` (page tabs with the `UI_Warbands` icon, containers `AccountBankTab_1`.., event `PLAYER_ACCOUNT_BANK_TAB_SLOTS_CHANGED(slot)`) and shows its tab only when `C_Bank.CanViewBank(Enum.BankType.Account)` is true
  - Whether the live game gives characters an account bank is not yet verified in game: ask `CanViewBank` at runtime, never assume either way
  - ForeverMarket (1.23, FRV-35) reads it while the bank is open: `C_Bank.CanViewBank(Enum.BankType.Account)`, then the containers of `C_Bank.FetchPurchasedBankTabIDs(Enum.BankType.Account)` through `C_Container`, when the bank opens, after every `BAG_UPDATE_DELAYED` while it is open (items moving in the bank fire `BAG_UPDATE`, which the bank panel refreshes on: `Mainline/BankFrameTemplates.lua`) and on `BANK_TABS_CHANGED`; never as it closes; every call in `pcall` (not yet verified in game)
  - `PLAYER_ACCOUNT_BANK_TAB_SLOTS_CHANGED(slot)` is about the bags in the account bank's slots (Camelot's `BankItemButtonBagMixin` refreshes `Enum.BagIndex.Accountbanktab` on it), not about the items in them
- `C_Item.GetItemCount(itemInfo, includeBank, includeUses, includeReagentBank, includeAccountBank)`: the account bank is a flag of its own (the fifth argument), every flag defaults to false
  - Whether `includeBank` counts the character bank tabs while the bank is closed (and right after a login) is not yet verified in game. ForeverMarket 1.35 (FRV-98, `trade/Sources.lua`) does not assume it: with the bank closed it asks whether some item of its last bank reading shows in the bank part (count with - without the bank) and uses the client's count only then (and when that reading holds no item), else its own last reading (`R.bank`); `/fm item <item>` says which one counted
- An empty bags reading was seen in game (FRV-73, 2026-11-20): ForeverMarket 1.23.5 saved `"t|"` (no item) for a character at a logout after a short session, while Bagnon's `BagBrother.lua`, written at the same logout, held items in bags 0 to 4. Its stamp was the logout's, so the read at `PLAYER_LOGOUT` found nothing: either the containers are gone by then, or the bag index was cached before the bags had loaded at login (no `BAG_UPDATE_DELAYED` after it). Which of the two is not known yet: since 1.31 ForeverMarket keeps the last reading instead, reads the bags afresh at login, and notes every skipped read (`charInfo[key].bagsEmpty` = `login,<t>` or `logout,<t>`, shown by `/fm chars`); a `bagsEmpty` of `logout` next to bags that did hold items settles it

## Mail

Verified against wow-ui-source `forever` (1.60.1) for FRV-37 (sending) and FRV-166 (taking mail out). In game ForeverMarket already reads the inbox (`GetInboxNumItems`, `GetInboxHeaderInfo`, `GetInboxInvoiceInfo`, `GetInboxItem` on `MAIL_INBOX_UPDATE`); everything about sending, and about taking mail out from AddOn code, is verified against the source only (not yet verified in game).

- The mail frame is Mainline's `Blizzard_MailFrame` on the global mail functions (they are not in `Blizzard_APIDocumentationGenerated/`, Blizzard's Lua uses them): `SendMail(recipient, subject, body, replyMailID)`, `GetSendMailItem(slot)` -> `itemName, itemID, itemTexture, stackCount, quality`, `HasSendMailItem(slot)`, slots 1 to `ATTACHMENTS_MAX_SEND` (12)
- `GetInboxNumItems()` returns the mails the inbox shows and the mails it holds in all (`numItems, totalItems`): the inbox can hold more than it shows
- Events (`MailInfoDocumentation.lua`): `MAIL_SEND_SUCCESS` after the server took a mail (the frame resets its send slots on it), `MAIL_FAILED(itemID)`, `MAIL_SEND_INFO_UPDATE` when the send slots change, `MAIL_INBOX_UPDATE`, `MAIL_SHOW`, `MAIL_CLOSED`
- A mail with money goes through the secure transfer confirmation (`C_SecureTransfer.SendMail` after `SendMail`), so `MAIL_SEND_SUCCESS` can come long after the `SendMail` call
- ForeverMarket (1.24, FRV-37) hooks `SendMail` with `hooksecurefunc`, reads the send slots right after the call and logs them on `MAIL_SEND_SUCCESS` for a mail to another character of the player
  - Assumed, not yet verified in game: the send slots still hold the items right after `SendMail` returns (the frame keeps them until `MAIL_SEND_SUCCESS`, and on `MAIL_FAILED` only re-enables its Send button), and the recipient is typed as the first name or the full name
- Taking mail out (FRV-166, `Blizzard_MailFrame/MailFrame.lua` and `MailFrame.xml` of 1.60.1.71037; how ForeverMarket hooks these calls, and what it assumes about them, is under [Auction House](#auction-house)). The take functions are globals outside `Blizzard_APIDocumentationGenerated/`, so no secret or restriction flag can be read for them; Blizzard's Lua uses them:
  - `TakeInboxMoney(index)` (the money button of an open mail, Open All), `TakeInboxItem(index, slot)` (an attachment button, Open All; slots 1 to `ATTACHMENTS_MAX_RECEIVE` = 16, `HasInboxItem(index, slot)` tells which hold something), `AutoLootMailItem(index)` (the modified click on an inbox row; by its name and that use it takes everything in the mail: assumed, not yet verified in game), `TakeInboxTextItem(index)` (the letter as an item), `DeleteInboxItem(index)` and `ReturnInboxItem(index)` (`InboxItemCanDelete(index)` decides which of the two the open mail's button does)
  - `GetInboxHeaderInfo(index)` returns `packageIcon, stationeryIcon, sender, subject, money, CODAmount, daysLeft, itemCount, wasRead, wasReturned, textCreated, canReply, isGM, firstItemQuantity, firstItemLink` (the names Blizzard's Lua gives them; `itemCount` is nil for a mail without items); `GetInboxText(index)` returns `bodyText, stationeryID1, stationeryID2, isTakeable, isInvoice, isConsortium`; `GetInboxItem(index, slot)` returns `name, itemID, texture, count, quality, canUse, isCurrency`; `C_Mail.HasInboxMoney(index)` is documented
  - A whole mail in one click is part of the default frame: an inbox row's `OnClick` (`MailItemTemplate`) asks `IsModifiedClick("MAILAUTOLOOTTOGGLE")` (default `SHIFT` in `Bindings_Camelot.xml`) and runs `InboxFrame_OnModifiedClick`: `AutoLootMailItem(index)` unless the mail is COD, then the plain click, which opens the mail
  - COD: `TakeInboxItem` on a COD mail is the payment. Blizzard asks before it (`COD_CONFIRMATION`, or `COD_ALERT` when the money is short, `Blizzard_StaticPopup_Game/GameDialogDefs.lua`), and both the modified click and Open All leave a COD mail alone. The same file defines `COD_CONFIRMATION_AUTO_LOOT`, which calls `AutoLootMailItem(index)` when accepted and which no Lua on the branch shows: `AutoLootMailItem` on a COD mail has to be taken for a payment too. AddOn code that takes mail reads `CODAmount` of the index right before every call, whichever of the two it makes
  - Open All (`OpenAllMailMixin`): `C_Mail.SetOpeningAll(true)` while it runs (what the client does with it is not documented); it skips mail from a GM (`isGM`) and COD mail, takes a mail's money first (`TakeInboxMoney`) and then its items from slot 16 down (`TakeInboxItem`), one call per step; after a call it waits at least `OPEN_ALL_MAIL_MIN_DELAY` = 0.15 s and then for as long as `C_Mail.IsCommandPending()` says yes, from its `OnUpdate` (so no hardware event per step); a `MAIL_INBOX_UPDATE` with another `GetInboxNumItems()` than at its start sends it back to mail 1 (a mail that leaves moves the ones below it up); an item of a `MAIL_FAILED(itemID)` is skipped for the rest of the run; it stops when `C_Container.CalculateTotalNumberOfFreeBagSlots()` is 0, on `MAIL_OPEN_ALL_CANCELED` and when its button hides. It never deletes or returns a mail
  - Its `OnClick` does not look at the mouse button: registering the Open All button for right clicks would start Open All on a right click
  - Results: `MAIL_SUCCESS(itemID)` and `MAIL_FAILED(itemID)` (`MailInfoDocumentation.lua`, the ID can be nil), `UI_ERROR_MESSAGE(errorType, message)` (`SystemDocumentation.lua`). `ERR_INV_FULL` is a global that Blizzard's Lua compares such a message with (`Blizzard_UIPanels_Game/Mainline/LootFrame.lua`); the branch holds no GlobalStrings, so other error texts (`ERR_ITEM_MAX_COUNT` for a unique item) cannot be checked against it
  - The inbox shows at most `MAX_INBOX_SIZE` = 100 mails (a local of `MailFrame.lua`): `InboxMixin:Update` asks for the list again (`MailFrame:RefreshInbox()`) while `numItems ~= totalItems` and fewer than 100 are shown, `InboxTooMuchMail` shows while the server holds more, and `InboxMixin:GetMoreMail` calls `CheckInbox()` while mail is left over and fewer are shown than before (at a page turn, and at a `MAIL_SUCCESS` while a next page exists). `MailMixin:RefreshInbox` asks `C_Mail.CanCheckInbox()` (`canCheckInbox, secondsUntilAllowed`) and waits that long with a timer. How many mails the Forever server sends per list and how long that wait is are not yet verified in game
  - A closed mail is deleted by the frame only when it holds nothing and its letter was taken as an item: `OpenMailMixin:OnHide` calls `DeleteInboxItem` when `money == 0 and not itemCount and textCreated`, a pending sale's `seller_temp_invoice` aside. Which emptied mails the server removes by itself is not yet verified in game
  - Bag room: `C_Container.GetContainerNumFreeSlots(bag)` returns `numFreeSlots, bagFamily` (`ContainerDocumentation.lua`; Blizzard's bag buttons take `bagFamily == 0` for a bag that holds any item, `Blizzard_MainMenuBarBagButtons/Shared/MainMenuBarBagButtons.lua`). `C_Container.CalculateTotalNumberOfFreeBagSlots()` returns `totalFreeSlots` (`ContainerDocumentation.lua`); which bags it counts the branch does not show (its three callers only read the number; not yet verified in game), so AddOn code that has to know whether a mail's item fits counts the free slots of the `bagFamily == 0` bags itself
  - Protected or not: nothing in the source binds a take call to a hardware event or to Blizzard's own code, and nothing in the mail frame's Lua looks at combat. AddOns that state Forever support drive the calls from their own `OnUpdate`: Parcel 1.8.1 (MIT, `Parcel_Camelot.toc` with interface 16001, read on GitHub 2026-11-25) calls `TakeInboxItem` and `TakeInboxMoney` from `Core/Queue.lua`, 0.30 s apart, waits for `C_Mail.IsCommandPending()` and compares `UI_ERROR_MESSAGE` with `ERR_INV_FULL` and `ERR_ITEM_MAX_COUNT`. Whether the Forever client lets AddOn code make these calls, also in combat, is not yet verified in game
  - Hooks: `hooksecurefunc("TakeInboxMoney", ...)` puts the hook into the global of that name, so code that kept the function in a local before the hook was made (ForeverMarket makes its hooks at `PLAYER_LOGIN`, after every AddOn's files ran) calls past it. AddOn code that takes mail calls the globals by name at the time of the call, as Blizzard's does
  - An inbox row's tooltip: while it is shown the row's `OnUpdate` builds it again every frame through the global `InboxFrameItem_OnEnter(self)`, so a line added by an `OnEnter` script is gone a frame later; a line of an AddOn goes in with `hooksecurefunc("InboxFrameItem_OnEnter", ...)`

## Professions

Verified against wow-ui-source `forever` (1.60.1) for FRV-10 and FRV-65, not yet verified in game. ForeverMarket takes the recipe list of its market table from the SavedVariables of the third-party AddOn ForeverArtisan; since 1.21 its craft log (`trade/Crafts.lua`) hooks `C_TradeSkillUI.CraftRecipe` and reads `C_TradeSkillUI.GetRecipeSchematic` (below).

- The profession window is Mainline's `Blizzard_Professions` with Camelot overrides, so recipes come from `C_TradeSkillUI`; the Classic Era functions (`GetNumTradeSkills`, `GetTradeSkillInfo`, `GetNumCrafts`, `GetCraftInfo`) appear nowhere in the branch
  - `C_TradeSkillUI.GetRecipeInfo(recipeSpellID)` returns a table with `learned`, `relativeDifficulty`, `recipeID`, ... (or nil); `C_TradeSkillUI.GetRecipeSchematic(recipeSpellID, isRecraft)` returns `outputItemID`, `quantityMin` / `quantityMax` and `reagentSlotSchematics`
  - A schematic's normal materials are the slots with `reagentType == Enum.CraftingReagentType.Basic` (1; `Modifying` 0, `Finishing` 2, `Automatic` 3): `reagents[1].itemID` and `quantityRequired` per craft (`Blizzard_ProfessionsTemplates/Blizzard_Professions.lua`, `Blizzard_ProfessionsTransaction.lua`)

The craft log's batch ended after 30 s without a change until 1.38.5, so no line was ever written for such recipes (also Comfortable Leather Hat, Turtle Scale Bracers, Tough Scorpid Breastplate and Shadowskin Gloves, crafted from 11/19 to 11/23 without a line); the product comes at the end of each cast (TradeskillQueue's `CRAFTED_RESULT` after `SUCCEEDED`)
  - Since 1.38.5 a batch stays open while `UnitCastingInfo("player")` reports a cast with `isTradeskill` (its sixth return, `NeverSecret` in `UnitDocumentation.lua`), and an idle batch waits 30 s plus the recipe's cast time (`C_Spell.GetSpellInfo(recipeID).castTime`). That the client reports a crafting cast that way is verified against the source only
  - `TRADE_SKILL_ITEM_CRAFTED_RESULT(data)` (`CraftingItemResultData`: `itemID`, `quantity`, `hyperlink`, ...) and `TRADE_SKILL_CRAFT_BEGIN(recipeSpellID)` exist, and Camelot keeps Blizzard's crafting output log that listens to the first (`Blizzard_Professions/Camelot/Blizzard_ProfessionsCraftingOutputLog.lua` only turns its auto open off); whether the server sends them for Forever's recipes is not verified in game, so ForeverMarket does not rely on them

Camelot's `SetControlAnchors` puts `CreateAllButton` at `BOTTOMLEFT` of the page's `BOTTOMRIGHT` -362, 7 and the count box `CreateMultipleInputBox` at -185, 11, `CreateButton` sits at `BOTTOMRIGHT` -9, 7, the recipe list is 304 wide from x 5 down to the bottom (`Camelot/Blizzard_ProfessionsCrafting.lua`, `Blizzard_ProfessionsCrafting.xml`); Camelot's side tabs (`ProfessionsOverviewTab`, `Professions1Tab`..) hang past the window's right edge (`Camelot/Blizzard_ProfessionsFrame.xml`)

  - The selected recipe: `ProfessionsFrame.CraftingPage.SchematicForm:GetRecipeInfo()`; the open profession: `C_TradeSkillUI.GetBaseProfessionInfo()` (`ProfessionInfo`: `professionID`, `professionName`, `parentProfessionID`, ...); `IsTradeSkillLinked()` and `IsTradeSkillGuild()` are used by Blizzard's Lua without generated documentation, `IsNPCCrafting()` and `GetRemainingRecasts()` (casts left of a batch) are documented; events `TRADE_SKILL_SHOW` / `TRADE_SKILL_CLOSE`

## Camping

Verified for FRV-116 against wow-ui-source `forever` (1.60.1) and the game data named below. Only the entry marked "seen in game" was checked in the live client (the maintainer's test of ForeverCampFeatures 1.0.11, 2026-11-23, FRV-124); the rest is not yet verified in game by this repository. ForeverCampFeatures relies on it; `/fcf debug` prints what the live client answers for each way.

- Game data (not in wow-ui-source; from ForeverArtisan's recipe data read in Forever's live profession windows, November 2026): every profession has three camp items crafted under "Camping" in its window (skill 20, 140 and 300), Cooking has the Basic, Journeyman and Expert Campfire kits, Cookie's Feast and the Iron Oven. Names, recipe spell IDs and item IDs are in `addons/ForeverCampFeatures/Data.lua` (Iron Oven: recipe 1263067, item 279982); the Fishing, Herbalism, Mining and Skinning items have no known IDs yet
  - A recipe and its camp item share the name ("Iron Oven" crafts "Iron Oven"); a campfire recipe crafts a kit ("Basic Campfire" 1229737 crafts "Basic Campfire Kit" 279981)
  - Using a camp item is a cast named after it: the maintainer's ForeverArtisan_Camping saved data maps the casts "Tanning Rack", "Fish Bowl", "Camp Tent" and "Camp Chair" to those items (`castNames`). A cast named like an object can therefore also be its craft
  - Recipes that need a camp object nearby, from the same data's tools column: 61 Blacksmithing recipes need "Master Forge" (Arcanite Reaper 16994, Arcanite Champion 16990, ...), Enchanting's Brilliant Wand (1248650), Torch of Light (1306520) and the Forever relics "Arcane Forge"; "Anvil" is also the world's anvils. Lobster Stew (18245) needs the Iron Oven on Forever (the maintainer in FRV-116; the vanilla recipe needed a cooking fire)
- Durations and rules (the community wiki https://wowcalc.net/en/forever/wiki/camping and the wow.gg camping guide, November 2026; not verified in game): every camp feature and campfire stays 15 minutes; features share a 60 minute cooldown, campfires have their own 5 minutes; features need a campfire nearby, the Iron Oven and Cookie's Feast a cooking fire; other players can use a placed object
- In range: `C_TradeSkillUI.GetRecipeRequirements(recipeID)` (`TradeSkillUIDocumentation.lua`, `SecretArguments = "AllowedWhenUntainted"`, no secret returns) returns `CraftingRecipeRequirement` tables `{ name, met, type }` with `Enum.RecipeRequirementType` `SpellFocus` 0, `Totem` 1, `Area` 2
  - Blizzard's schematic form colors the "Requires: ..." line red by `met` and reads the requirements again "on every update because it contains the updated .met field" (`Blizzard_ProfessionsTemplates/Blizzard_ProfessionsRecipeSchematicForm.lua`); the crafting page will not craft while one is not met (`ValidateCraftRequirements` in `Blizzard_Professions/Blizzard_ProfessionsCrafting.lua`)
  - Seen in game (the maintainer's test of ForeverCampFeatures 1.0.11, 2026-11-23, FRV-116 and FRV-124): it answers while the profession window is closed. Standing at an Iron Oven with the Cooking window closed, the requirement "Iron Oven" of Lobster Stew (18245) came back met, and ForeverCampFeatures' once-a-second check found the oven in range. The test was set up for a character who knows the recipe, but the answer did not record which character it was (ForeverCampFeatures asks 18245 whether the recipe is known or not)
  - Still not settled: whether it answers for a recipe the character does not know. `/fcf debug` prints each asked recipe's answer with the window's state, and `C_Spell.IsSpellUsable(recipeID)` ("Returns whether the spell is currently castable; Typically based on things like learned status, required resources") next to it as the other candidate
- Hover: `WORLD_CURSOR_TOOLTIP_UPDATE(anchorType)` fires when "the mouse enters or leaves something in-world (object, unit, etc) that should display a tooltip" (`CursorDocumentation.lua`); Blizzard answers it with `GameTooltip:SetWorldCursor`, which reads `C_TooltipInfo.GetWorldCursor()` (`MayReturnNothing`, no secret flag; `type` is an `Enum.TooltipDataType`, `Object` 4, `Unit` 2, and `lines[1].leftText` the name), `Blizzard_GameTooltip/Mainline/GameTooltip.lua`
  - Blizzard's comment there expects world cursor data with "secret line data/text", so check each part with `issecretvalue`; the data names the thing and gives no position
  - Calling `GetWorldCursor` from an AddOn's own event handler leaves `GameTooltip` untouched (ForeverCampFeatures does not hook it)
- Your own placement: `UNIT_SPELLCAST_SUCCEEDED` of the player (Spell casts above); `C_Item.GetItemSpell(itemID)` returns a camp item's use spell (`spellName, spellID`, `MayReturnNothing`) once the item's data is loaded (`C_Item.RequestLoadItemDataByID`, then `ITEM_DATA_LOAD_RESULT(itemID, success)`)
- Positions and distances: `C_Map.GetPlayerMapPosition(uiMapID, "player")` (a vector2 on any map that holds you, nil where the client gives none) and `C_Map.GetMapWorldSize(uiMapID)` ("the size in yards of the area represented by the map"), neither flagged secret
- No API lists the game objects around the player, and other players' casts can be secret (Spell casts above), so an AddOn cannot see another player place an object

## AddOn list

- `Blizzard_AddOnList/AddonList.lua` reads these `.toc` fields:
  - `## IconTexture:` (texture path or file ID) or `## IconAtlas:` puts an icon before the title, without them the list shows `INV_Misc_QuestionMark`
  - `## Category:` puts AddOns under one collapsible category header (categories are sorted alphabetically above the uncategorized AddOns, the header's right-click menu has Enable all / Disable all / Reset to default); no AddOn depends on another for this
  - `## Group:` nests an AddOn under another *installed* AddOn whose folder name matches exactly (seen in game with the multi-part ForeverArtisan and its "Core"); the client sets it automatically for AddOns with similar names and dependencies, children with a missing parent fall back to the top level outside any category
- Reading the AddOn list in code (verified against the source for FRV-180, not yet verified in game): `C_AddOns.GetNumAddOns()`, `C_AddOns.GetAddOnInfo(index)` (name first), `C_AddOns.GetAddOnMetadata(index, "Category")` (Blizzard's AddOn list reads it so, by index) and `"Version"`, `C_AddOns.IsAddOnLoaded(index)` (`loadedOrLoading, loaded`) and `C_AddOns.IsAddOnLoadOnDemand(index)`; none is flagged secret or `HasRestrictions` (`AddOnsDocumentation.lua`, `SecretArguments = "AllowedWhenUntainted"`). ForeverMarket_Feed has `## Category: Jim's Forever AddOns` and `## LoadOnDemand: 1`
- One SavedVariables name in several AddOns (FRV-120's `JimsForeverAddOnsDB`; the usual client behavior, not yet verified in game): each AddOn that lists it keeps its own copy in its own file; the client runs an AddOn's file when it loads that AddOn, just before its `ADDON_LOADED`, so the global holds that AddOn's copy at that moment and the last AddOn loaded wins, and at logout the global as it is then is written into every one of those files. The shared file therefore picks the copy with the newest `updated` stamp at each carrier's `ADDON_LOADED` and sets the global back to it
- `## Dependencies:` (verified against the source for FRV-175, not yet verified in game for ForeverMarket; Blizzard's own `.toc` files and ForeverArtisan's profession folders use it): an AddOn whose required dependency is missing or disabled is not loadable. `Blizzard_AddOnList/AddonList.lua` shows its reason from `C_AddOns.IsAddOnLoadable` as `_G["ADDON_" .. reason]` (`DEP_MISSING`, `DEP_DISABLED`), its title red (enabled, not loadable) or grey (`DEP_DISABLED`), and the dependencies in its tooltip (`AddonTooltip_BuildDeps`, `C_AddOns.GetAddOnDependencies`); `## OptionalDeps:` only makes an installed AddOn load first. ForeverMarket 1.48 requires `ForeverArtisan_Core` (the folder every ForeverArtisan install has, titled "Core (Required)", CurseForge project 1716370) and lists the ForeverArtisan folders it reads as optional
- SavedVariables files are named after the AddOn folder (`WTF/Account/<account>/SavedVariables/<AddOnName>.lua`, seen on the maintainer's client), so a renamed AddOn starts with a new file and the old one stays unused; the variable name inside must match the `## SavedVariables:` name too

## Keyboard and mouse state

Verified against wow-ui-source `forever` (1.60.1) for FRV-155, not yet verified in game. ForeverMarket 1.47 showed the market table's tooltips only while Shift is held, since 1.48 (FRV-186) only those of its inputs, dropdowns and checkboxes (`ui/Filters.lua`).

- `MODIFIER_STATE_CHANGED(key, down)` (`KeyBindingsDocumentation.lua`, a synchronous event, no secret flag): `key` is a string such as `LSHIFT`, `RSHIFT`, `LCTRL`, `LALT`, `down` a number (1 pressed, 0 released)
- `IsShiftKeyDown()`, `IsControlKeyDown()`, `IsAltKeyDown()` and `IsModifierKeyDown()` are documented in `InputDocumentation.lua`
- `GetMouseFoci()` (`InputDocumentation.lua`) returns a table of the regions under the mouse; `GetMouseFocus()` (the older single-frame form) is not in `Blizzard_APIDocumentationGenerated/` and is called only in a WoWLabs file (`Blizzard_ActionBar/WoWLabs/ActionButtonOverrides.lua`), which Camelot does not load: treat it as gone and use `GetMouseFoci()`. ForeverMarket does not need either: its tooltip helper remembers the element from its own `OnEnter` / `OnLeave` and checks `IsVisible()` and `IsMouseOver()` when Shift changes
- `GetCurrentKeyBoardFocus()` is not in `Blizzard_APIDocumentationGenerated/`, but Blizzard's Lua calls it (`Blizzard_Game/Mainline/EventImplementation.lua`), so it exists: the frame with the keyboard focus, or nil. It can be a frame an AddOn may not touch: check `IsForbidden()` (`SimpleFrameScriptObjectAPIDocumentation.lua`) before calling anything else on it. On a frame that is not your own, `IsForbidden()`, `GetName()` and `GetParent()` are flagged `SecretReturnsForAspect` (ObjectSecurity, ObjectName, Hierarchy; `SimpleFrameScriptObjectAPIDocumentation.lua`, `SimpleObjectAPIDocumentation.lua`): test each result with `issecretvalue` before comparing it or using it as a table key (ForeverMarket's `TypingHere` walks the parents of the focused frame that way)
- An `EditBox` that is a child of a `Button` takes its own mouse clicks, so the button's `OnClick` does not run for them; `EnableMouseWheel(true)` with an `OnMouseWheel` script lets the wheel over it scroll the list behind (ForeverMarket's Amount inputs in the Picks rows, FRV-154; `HighlightText`, `SetTextColor` and `SetTextInsets` are in `SimpleEditBoxAPIDocumentation.lua`)

## Taint

- Never write fields onto Blizzard frames (for example `SomeBlizzardFrame.RegisterEvent = function() end`) that handle secret data, it taints Blizzard code and causes secret value errors or "AddOn has been blocked from an action" popups
- Use `hooksecurefunc` / `frame:HookScript` instead of replacing Blizzard functions or scripts
- Debugging: Lua errors with stack traces end up in `_forever_/Logs/General.log`; `/console taintLog 1` writes `Logs/taint.log`
