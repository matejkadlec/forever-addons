# ForeverCraftQueue (`addons/ForeverCraftQueue/`)

> **Scope:** the ForeverCraftQueue AddOn. The root [`AGENTS.md`](../../AGENTS.md) and [`addons/AGENTS.md`](../AGENTS.md) apply here and are not repeated.
>
> **Maintenance:** update this guide when a file, a step of Process queue, the saved data, a slash command or the hooks into Blizzard's profession window change; the user-facing description lives in the root [`README.md`](../../README.md).

A crafting queue across all professions (FRV-131, label `forever-craft-queue`, shortname FCQ, `/fcq`). The idea comes from Advanced Trade Skill Window (ATSW, 3.3.5), which has no license: **take ideas only, never its code**. Nothing of ATSW is copied, ported or translated into this folder; every line is written for Forever's API.

## The profession window

- Forever's profession window is Mainline's `ProfessionsFrame` (`Blizzard_Professions`, load on demand) with Camelot overrides, not the classic `TradeSkillFrame`; its crafting page has `CreateAllButton`, `CreateMultipleInputBox` (the count box) and `CreateButton` at the bottom right, the recipe list (304 px) on the left, and side tabs past the window's right edge
- The AddOn only reads that page (`SchematicForm:GetRecipeInfo()`, `GetCraftableCount()`, `CreateButton:IsShown()`, `CreateAllButton:GetWidth()`) and hooks it with `hooksecurefunc(page, "ValidateControls", ...)` and `HookScript`; it writes no field onto Blizzard's frames
- "Add all to queue" and "Open queue" are child buttons of the page in a row above Create All, made from the page's own button template (`page:GetButtonTemplate()`, Camelot's `SharedButtonSmallTemplate`: the red three-slice button with the golden border that Create All uses)
  - Add all to queue starts at Create All's left edge and is as wide as Create All (which only grows, with its count's digits), or as wide as its own text plus the template's padding when that is more (FRV-197: the longer label next to a short "Create All [5]"), and as high; its vertical middle is the Track Recipe checkbox's (`SchematicForm.TrackRecipeCheckbox`, the maintainer's choice after his test of 1.0.3). Two invisible frames of the AddOn carry the anchors: one from Create All's bottom left corner to the middle of the checkbox's right edge, one cut from it to Create All's width; without the checkbox the row sits 4 px above Create All
  - Open queue sits right of it, as wide as its text plus the template's padding: a Create All wide one would reach the Track Recipe checkbox at the schematic form's bottom right
  - Their frame level is the schematic form's + 2: the first build sat at the page's level left of Create All, over the recipe list, and the game showed only its text, not its red textures (most likely the list's art at the same level drawn over them)
  - Add all to queue shows while Blizzard shows Create (a learned recipe in your own window) and is disabled while its count is 0 (`SetMotionScriptsWhileDisabled`, so its tooltip still shows and says why); Open queue whenever the AddOn is on
- The panel opens only when asked for (Open queue, `/fcq`, the binding, Clear queue's confirmation), or with the option `autoOpen` ("Open queue window automatically", off by default) also with the profession window and on Add all to queue; an open panel docks when the profession window opens and a docked one closes with it
- Add all to queue's count is what Create All shows (FRV-197): the page's own `GetCraftableCount()` (`Blizzard_ProfessionsCrafting.lua`, not overridden by Camelot), the number `ValidateControls` formats into "Create All [19]"; the count box is not read. The AddOn calls it in `pcall` from its click, its tooltip and its `ValidateControls` hook (Blizzard runs `ValidateControls` on `BAG_UPDATE`, so the button's state follows the bags)
  - That function only reads: the transaction's getters and `ProfessionsUtil.GetReagentQuantityInPossession` (`ItemUtil.GetCraftingReagentCount`); its one write is a salvage item's `assertShown` (salvage recipes came with Dragonflight; vanilla's professions have none)
  - When the page cannot answer (no method, an error, no number), the count is `C_TradeSkillUI.GetCraftableCount(recipeID)`, the count after a recipe's name in the list; else 0
  - A recipe already in the queue is set to that count (`ns.QueueRecipe`), not added on top; the chat line says "Craft queue updated: ... x19 (was x5)"

## Process queue

One press crafts the queue (FRV-220, 1.3.0; before it every row took a press, FRV-131's rule "one step per press, never a loop, never a timer that crafts"). The press (the panel's button, the binding, a mouse wheel step while a run waits) starts a **run**; the run starts each next row when the batch before it ends and opens another profession when a row needs it. `Core.lua` holds the run as a state machine without game calls (`ns.RunnerPress`, `ns.RunnerStep`, `ns.RunnerCast`, `ns.RunnerError`, `ns.RunnerBlocked`, `ns.RunnerRefuse`, `ns.RunnerHalt`); `ForeverCraftQueue.lua` tells it what happened and carries out the one action it answers with (`Perform`), looking at the game every 0.2 s from the event frame's `OnUpdate` while a run goes (`ns.Tick`; no `OnUpdate` while none goes).

- **Whether the game allows it without a key press is found out in the game, not assumed.** The generated documentation flags neither `C_TradeSkillUI.CraftRecipe` nor `OpenTradeSkill` with `HasRestrictions`; warcraft.wiki.gg (retail, read 2026-11-27) marks `OpenTradeSkill` `#hwevent` and `CraftRecipe` not; ForeverFishing 0.9.251 (a live Forever AddOn) asks for a press per meal ("Press Start for the next meal"). So the run tries a start without a press and watches what follows:
  - a cast of the row's recipe starts (or the profession is open): it works, remembered as `auto.craft` / `auto.open` = true
  - nothing starts within `ns.START_WAIT` (3 s) / `ns.OPEN_WAIT` (5 s) and the game said nothing: the run **waits for a press** (button "Continue", a chat line, the alert sound, the mouse wheel catcher); when that press then does it, the refused try counts, and `ns.AUTO_STRIKES` (2) of those in a row, with no working try between, set `auto.craft` / `auto.open` = false: from then on no try, the wait for a press is ready the moment a batch ends
  - `ADDON_ACTION_BLOCKED` / `ADDON_ACTION_FORBIDDEN` naming the AddOn's call: false at once, the event and function kept in `auto.blocked`
  - the game's own error text (`UI_ERROR_MESSAGE`: full bags, a missing tool, moving) with a start that does not begin: the run ends with that text, it is no matter of key presses
  - the record is per client build (`GetBuildInfo`): another build starts afresh; the settings page shows it and "Try again" forgets it (`ns.ResetAuto`). Each change is said once in the chat
- **The next row** is the first one with materials for at least one craft and not on cooldown (`ns.NextStep`; a cooldown is `C_TradeSkillUI.GetRecipeCooldown` with no charges left, what Blizzard's Create checks in `Professions.IsRecipeOnCooldown`; transmutes, Mooncloth, Cured Rugged Hide). Blizzard asks it only for the open profession's recipes, so the AddOn remembers when each cooldown it saw ends and uses that while the recipe's own profession is closed (else a run would open that profession only to pass the row over and switch back); its own open window saying ready forgets it
  - Its profession open for your own crafting (`TRADE_SKILL_SHOW` seen and no `TRADE_SKILL_CLOSE` since, `GetBaseProfessionInfo().professionID` is the row's skill line, not loading, not linked, guild or NPC crafting): `C_TradeSkillUI.CraftRecipe(recipeID, casts)` with `casts` = the row's count or what the bags allow; a recipe `GetRecipeInfo` says is not learned, or a requirement of `GetRecipeRequirements` that is not met, ends the run with a line
  - Else `C_TradeSkillUI.OpenTradeSkill(skillLine)` (the base profession's ID, as Blizzard's `OpenProfessionUIToSkillLine` passes it), then the craft once `ns.OpenSkillLine()` is the row's. A press that opens a profession asks the run again inside the same press (`TRADE_SKILL_SHOW` is a synchronous event and can run inside the call), so one press opens and crafts where the window is there at once
  - From a press on a click or key the call is verified in game (2026-11-24, 1.0.4: opening with no window and with another profession open, no blocked popup; ForeverMarket's FRV-132 test covered the side tabs after an AddOn's opening, `docs/forever-api-notes.md`); it needs no secure action button. Without a press it is what FRV-220's in-game test finds out
- **A batch is over** when no craft of yours runs (`ns.IsCrafting`: `UnitCastingInfo`'s `isTradeskill`, or `GetRemainingRecasts() > 0` with a cast event in the last 3 s, so a count left standing by a batch that ended early does not hold the run) for `ns.SETTLE` (0.5 s) after its last cast event (the product reaches the bags after the cast). `UPDATE_TRADESKILL_CAST_STOPPED` is only written to the trace: when Forever sends it is not verified
  - The run's own batch counts the successful casts of its recipe: fewer than asked for is an **early end** (an interrupt, moving, full bags) and ends the run with the game's error text when one came
  - A craft the run did not start (Blizzard's Create, a batch from before) never starts or locks anything: its casts of queued recipes leave the queue as always, and a press during it joins it (the run goes on when it ends)
- **The run ends by itself**, with the reason in the panel's status line ("Stopped: missing 3 Salt for Cured Light Hide. Process queue goes on from here."), a chat line and the alert sound, and the rest stays queued: no row with materials (`ns.ShortText`: what the first row lacks for all its crafts left) or only rows on cooldown, a fight (`PLAYER_REGEN_DISABLED`), moving or another cast when the next row would start (`IsPlayerMoving`, a cast that is no craft), the profession window closed and still closed 0.5 s later while a batch runs or the run waits (a window that only switches professions closes and shows again, and `TRADE_SKILL_CLOSE` while the run itself opens a profession is its own), a start the game refuses, an early end, the queue emptied or the AddOn turned off (those two without a word)
- **Stop:** while a run goes the button reads "Stop"; a press (also the binding) lets the current batch finish and ends the run after it, a second press takes that back. A waiting run reads "Continue"
- **The mouse wheel** (option `wheel`, on by default): while a run waits for a press, an invisible full-screen frame at `TOOLTIP` strata takes the wheel (`EnableMouseWheel(true)`, `SetMouseClickEnabled(false)`, `SetMouseMotionEnabled(false)`: clicks and hover pass through), as ForeverMarket's sniper does for its purchases (seen in game there, FRV-82); one step is the press. It is shown only in that state, so nothing else loses its wheel
- Refused: in combat (the button is disabled and reads "In combat"), while the AddOn is off
- **The trace:** `ForeverCraftQueueDB.trace` keeps the last 80 lines of what the runs did and saw (presses, each call with "from a press" / "without a press", the window's events, blocked calls, the game's error texts, why a run ended, what was learned); `/fcq debug` prints its last 12 with the run's state and the `auto` record. After an in-game test the saved file answers what the game did
- The batch's cast bar: Process queue calls `CraftRecipe` itself, not Blizzard's `CreateInternal`, so a cast bar that learns the batch size only from the crafting page sees single crafts. Quartz's Tradeskill Merge (the maintainer's bar, one bar with the total time; its time text counts down, "2:35 / 2:38" is 3 s into a batch) hooks `C_TradeSkillUI.CraftRecipe` since 3.7.9-forever2 (asked in his test of 1.0.4), so a run's batch shows like Create All; Blizzard's own player cast bar shows one craft at a time for both
- Crafts leave the queue on the player's `UNIT_SPELLCAST_SUCCEEDED` whose spell ID is a queued recipe ID (secret IDs are ignored); any successful cast of a queued recipe counts, also one from Blizzard's Create
- Material counts come from `ItemUtil.GetCraftingReagentCount(itemID, false)`, the count Blizzard's Create buttons use, else `C_Item.GetItemCount(itemID)`
- The docked panel: Camelot's window hides when a trade skill closes (`ProfessionsMixin:OnTradeSkillClosed`), which would close the docked panel in the middle of a run that switches professions; a window that shows again within 1 s brings the panel it closed back (`Panel.lua`)

## Saved data

- `ForeverCraftQueueSettings` (account): `enabled`, `dock`, `autoOpen` (false by default), `confirmClear`, `doneSound` (also the alert sound of a run that stops or waits), `wheel` (booleans), `panelPos` (`{ point, relPoint, x, y }` of the free panel, nil = centered), `auto` (what the game allowed without a key press: `craft`, `open` = true / false / nil, `craftStrikes`, `openStrikes`, `blocked`, `build`; cleaned by `ns.CleanAuto`, dropped when the client build changes)
- `ForeverCraftQueueDB` (per character): `queue`, a list of rows `{ recipeID, name, icon, count, skillLine, profession, reagents = { { itemID, need, name } } }`; cleaned at load (`ns.CleanQueue`: broken rows dropped, a recipe twice merged, counts 1 to 9999); `trace`, the last 80 lines of the runs (strings; anything else dropped at load)
- A change of the row format needs a migration in `InitializeSavedData` and tests; the queue is the player's plan, not data that cannot be recreated
